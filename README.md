# Ассемблер учебной виртуальной машины

Реализован **этап 1** из `task.md`: CLI читает программу на JSON, проверяет команды
и преобразует их в промежуточное представление — список словарей с полями `A` и `B`.
В режиме тестирования это представление выводится в стандартный поток вывода.

## Требования и запуск

Нужны Go 1.22 или новее и Bash. Сторонних зависимостей нет.
Запуск и управление проектом выполняются через исполняемый файл `run.sh`.

```sh
./run.sh run -input tests/fixtures/load_const.json -output program.bin -test
```

Результат:

```json
[
  {
    "A": 128,
    "B": 46
  }
]
```

Команды управления:

| Команда | Назначение |
| --- | --- |
| `./run.sh` или `./run.sh help` | Показать справку по управлению проектом. |
| `./run.sh run <аргументы CLI>` | Собрать и запустить ассемблер. |
| `./run.sh build` | Собрать CLI в `build/assembler`. |
| `./run.sh test` | Запустить все тесты. |
| `./run.sh check` | Запустить все тесты и статический анализ `go vet`. |
| `./run.sh fmt` | Отформатировать Go-код. |
| `./run.sh clean` | Удалить каталог сборки `build/`. |

Флаги ассемблера можно передавать без команды `run`:

```sh
./run.sh -input tests/fixtures/read_mem.json -output program.bin -test
```

`run` перед каждым запуском собирает актуальные исходники. Каталог `build/` исключён
через `.gitignore`. Скрипт можно вызывать из любого каталога: Go-команды выполняются
в корне проекта, а относительные пути `-input` и `-output` считаются от текущего
каталога пользователя. Пути с пробелами следует заключать в кавычки.

Для `test` и `check` можно указать флаги тестирования, например `./run.sh test -v`
или `./run.sh check -race`. Путь к Go можно задать через переменную окружения:
`GO=/path/to/go ./run.sh build`. Справка и очистка работают без установленного Go.
Makefile сохранён для совместимости: его цели вызывают `run.sh`.

## Аргументы CLI

| Флаг | Назначение |
| --- | --- |
| `-input <путь>` | Обязательный путь к исходному JSON-файлу. |
| `-output <путь>` | Обязательный путь к будущему бинарному файлу. |
| `-test` | Вывести промежуточное представление в формате JSON. По умолчанию выключен. |
| `-h` | Показать справку. |

На этапе 1 путь `-output` только принимается: файл не создаётся, существующий файл
не изменяется, родительские каталоги не создаются. Формирование машинного кода,
вывод байтов и размера бинарника относятся к этапу 2. Интерпретатор, исполнение
команд и операции над векторами относятся к следующим этапам.

Без `-test` ассемблер проверяет исходник и строит внутреннее представление без вывода
при успехе. Диагностика и справка направляются в stderr. Коды завершения собранного
приложения: `0` — успех или справка, `1` — ошибка чтения, исходника или вывода,
`2` — ошибка аргументов. `run.sh run` сохраняет код завершения приложения;
при ошибке сборки запуск прекращается. Неизвестная команда скрипта возвращает код `2`.

## Язык исходной программы

Исходник в UTF-8 содержит один JSON-массив объектов. Каждый объект задаёт одну
команду через строковое поле `command`. Порядок объектов определяет порядок команд.
Пустая программа `[]` допустима. Имена команд и полей чувствительны к регистру.
Комментарии и завершающие запятые не допускаются правилами JSON.

| Команда | Обязательные поля | Поле `A` | Диапазон поля `B` |
| --- | --- | --- | --- |
| `load_const` | `command`, `value` | 128 | 0–16777215, биты 8–31 |
| `read_mem` | `command`, `address` | 199 | 0–131071, биты 8–24 |
| `write_mem` | `command`, `offset` | 83 | 0–16383, биты 8–21 |
| `sub` | `command` | 165 | Поле отсутствует |

Значения `value`, `address` и `offset` записываются целыми неотрицательными JSON-числами.
Знаковое представление в спецификации не определено, поэтому используются
беззнаковые диапазоны соответствующих битовых полей. Строки, дроби, экспоненциальная
запись, `null`, отсутствующие операнды и лишние поля отклоняются. У `sub` операндов нет.

Пример программы:

```json
[
  {"command": "load_const", "value": 46},
  {"command": "read_mem", "address": 95}
]
```

При проверке учитывается только структура команд. Наличие данных в памяти и состояние
стека на этапе 1 не проверяются. Например, отдельная команда `sub` допустима как исходник,
хотя для её будущего исполнения потребуются операнды на стеке.

## Промежуточное представление

В Go тип `assembler.Program` определён как `[]map[string]uint32`.
Поле `A` содержит опкод, поле `B` — константу, адрес или смещение.
Для `sub` словарь содержит только `A`. Значения сохраняются как числа;
упаковка в четырёхбайтовые команды на этом этапе не производится.

Примеры из спецификации:

| Исходная команда | Словарь промежуточного представления |
| --- | --- |
| `{"command":"load_const","value":46}` | `{"A":128,"B":46}` |
| `{"command":"read_mem","address":95}` | `{"A":199,"B":95}` |
| `{"command":"write_mem","offset":881}` | `{"A":83,"B":881}` |
| `{"command":"sub"}` | `{"A":165}` |

При ошибке преобразование отклоняется целиком; частичный результат не выводится.
Диагностика ошибки команды содержит её номер, начиная с 1.

## Проверки

```sh
./run.sh check
```

Команда запускает `go test ./...` и `go vet ./...`. Тесты проверяют все четыре примера
спецификации на уровне промежуточного представления, порядок команд, границы операндов,
ошибочный JSON, некорректные поля и аргументы CLI. Отдельно проверяются тестовый режим,
сохранность существующего выходного файла и отсутствие создаваемых файлов и каталогов.
Проверка эталонных байтов относится к этапу 2.

```text
src/
  main.go                 Точка входа CLI
  assembler/              Спецификация команд и JSON-парсер
  cli/                    Аргументы, чтение файла, вывод результата
tests/
  fixtures/               Четыре исходника из примеров спецификации
  parser_test.go          Проверки преобразования и валидации
  cli_test.go             Проверки CLI и отсутствия записи бинарника
run.sh                    Запуск, сборка, проверки, форматирование и очистка
```

Форматирование: `./run.sh fmt`. Исходники соблюдают ограничения на длину файлов, строк,
функций, число аргументов и цикломатическую сложность, перечисленные в `task.md`.
